1. The 10-Second Elevator Pitch (Start Here!)

"Think of RepoLens like Grammarly, but for code security."

Just like Grammarly underlines your grammar mistakes and lets you fix them with one click, RepoLens connects to your GitHub repository, underlines your security bugs, explains them in plain English, and fixes them with a 1-click Pull Request directly on GitHub!

🗣️ Perfect 30-Second Answer: "Tell me about your project"
"Sir, my project is called RepoLens. It is a full-stack MERN web application that acts as an automated security assistant for developers.

When a developer connects their GitHub repository, RepoLens scans the code for hardcoded passwords/API keys, vulnerable npm packages, and unsafe code patterns like command injection. It computes an overall Security Health Score from 0 to 100.

Instead of showing cryptic error codes, it uses AI to explain the risk in plain English, shows the exact line of bad code, and provides a 1-click button to automatically create a Pull Request on GitHub that fixes the bug.

I built the frontend with React and Vite in dark mode, the backend with Node.js and Express, and stored scans, findings, and user data in MongoDB."

3. What Does RepoLens Actually Scan? (AST vs. Regex)

RepoLens uses two distinct scanning techniques to balance high speed and deep accuracy:

Scan Category Method Used How It Works in Plain English
Dangerous Code (Command Injection, Eval) AST Abstract Syntax Tree RepoLens parses the JavaScript/TypeScript code into a grammatical tree (AST) using Babel. It checks if functions like child_process.exec() receive dynamic string concatenations or variables instead of safe static strings.
Missing Express Headers AST Abstract Syntax Tree Traverses the server startup code to verify whether security middleware like helmet() is enabled before routes are mounted.
Hardcoded Secrets & API Keys Regex + Shannon Entropy Matches known patterns (e.g., ghp_ for GitHub tokens, AKIA for AWS keys) and measures Shannon Entropy (randomness) to catch passwords and private tokens.
Vulnerable Dependencies API OSV.dev Database Reads package.json and queries the Google Open Source Vulnerabilities (OSV) API in batches to find known security advisories (CVEs).
License Compliance & SBOM Audit CycloneDX v1.5 Exports a standard Software Bill of Materials (SBOM) and warns against viral Copyleft licenses (GPL/AGPL) that could force commercial code to become open-source.

4. The Latest Engineering Updates & How We Solved Them

✨ Update 1: Smart Placeholder Filtering (Zero False Positives)

The Problem: When developers write tutorial or template connection strings like MONGODB_URI=mongodb+srv://<username>:<password>@cluster..., naive scanners mistakenly flagged them as critical leaked secrets.
The Solution: We implemented smart heuristic filtering in secretsScanner.ts. It detects placeholder markers (such as <username>, <password>, user:pass, YOUR_API_KEY) and automatically ignores them.

⚡ Update 2: High-Performance In-Memory OSV Caching

The Problem: Re-scanning a repo or scanning multiple branches was making repetitive external HTTP calls to https://api.osv.dev, which slowed down scans.
The Solution: Added an in-memory TTL cache (1-hour expiry) in dependencyScanner.ts. If a package (e.g. vitest@3.2.7) was checked recently, results are served instantly from memory in under 5ms.

🔒 Update 3: Enterprise Webhook & Route Security

Constant-Time Signatures: GitHub Webhook signatures (X-Hub-Signature-256) are verified using Node's crypto.timingSafeEqual to prevent timing-based side-channel attacks.
Rate Limiting: Added strict rate limiters on AI and PR-creation endpoints to protect backend resources and prevent API cost runaway.
Automated CI Pipeline: Added .github/workflows/ci.yml to run tests, linting, and production builds automatically on every push.

💡 Update 4: The Vercel PR #1 Bug Fix (The Best Story for Interviews!)

The Real Bug: When the user first clicked "1-Click PR" to upgrade vitest, RepoLens generated a pull request that failed on Vercel with Command "npm install" exited with 1.
Why Did It Break? The older AI replacement added a trailing comment inside package.json (e.g. "vitest": "^3.2.8" // safe version). Because standard JSON does not allow comments, Node's package manager crashed on syntax parsing!
How We Solved It: In githubClient.ts, we refactored the PR creator to parse package.json strictly with JSON.parse(), update the dependency key programmatically, and serialize it back with JSON.stringify(). Clean, 100% valid JSON with zero broken builds!

5. Top 10 Interview Questions & Winning Answers

Q1: What was your specific role and contribution?
Say this: "I worked as a Full-Stack developer. I built the React 18 UI with Tailwind CSS and Vite, created the Express REST APIs in TypeScript, implemented GitHub OAuth 2.0 with AES-256 encrypted tokens, built the background scanner for secrets and AST code patterns, and integrated the 1-click GitHub PR automation."
Q2: How does the 1-click "Create Fix PR" feature work under the hood?
Say this: "When the user clicks 'Create Fix PR', our backend retrieves the user's encrypted GitHub token, decrypts it in memory, and uses GitHub's Git Data API. It retrieves the latest commit SHA of the base branch, creates a new branch, updates the affected file with safe replacement code, commits the change, and opens a ready-to-merge Pull Request. The user is returned a direct link to review and merge the PR."
Q3: How do you avoid false positives when scanning code?
Say this: "We use two strategies: First, for code patterns, we use AST analysis instead of simple regex. AST parses the code into syntax trees, so it only flags functions like exec() when they actually receive dynamic variables, not when they run static safe commands. Second, for secrets, we built a smart placeholder filter that ignores documentation strings like mongodb+srv://<username>:<password>...."
Q4: Tell me about a real bug you encountered and how you solved it.
Say this: "When testing our 1-click PR feature on an external repo, Vercel's automated preview build failed with an npm install error. I investigated the pull request and realized our string-replacement logic had inserted a JavaScript comment (// safe version) inside package.json. Because standard JSON forbids comments, npm install couldn't parse the file. I fixed it by replacing raw string matching with structured JSON parsing—using JSON.parse, bumping the version cleanly in memory, and writing it back with JSON.stringify."
Q5: How is user authentication handled? How do you keep GitHub tokens safe?
Say this: "We use GitHub OAuth 2.0 with minimal scopes (read:user, user:email, public_repo). When GitHub returns an access token, we never store it in plain text. We encrypt it using AES-256-GCM with a unique 12-byte initialization vector and auth tag before saving it to MongoDB. For user sessions, we use signed HTTP-only cookies and double-submit CSRF tokens to block cross-site request forgery."
Q6: How does the Security Score calculation work?
Say this: "Every repository starts with a clean baseline score of 100. We deduct points based on severity: 25 for Critical, 15 for High, 5 for Medium, and 2 for Low. The final score is clamped between 0 and 100. If a user marks an issue as 'Resolved' or 'Ignored', the score recalculates dynamically in real time."
Q7: What is "Security Regression Detection"?
Say this: "Regression detection monitors how your security score changes over time across git commits. If commit A had a score of 95, but a developer pushes commit B that drops the score to 75 by introducing a new vulnerability, RepoLens flags a scoreDelta of -20 and alerts the developer with a prominent banner so they can fix the newly introduced issue before it hits production."
Q8: Why did you choose MongoDB instead of PostgreSQL or MySQL?
Say this: "Security findings have highly dynamic, nested attributes—a secret finding has line numbers and entropy; a dependency finding has CVE numbers, affected versions, and fixed versions. MongoDB's document model stores these polymorphic finding structures natively without requiring dozens of relational JOIN tables."
Q9: What happens if a scan takes a long time? Does it block the server?
Say this: "No. We designed an asynchronous background queue backed by MongoDB (MongoScanQueue). When the user clicks 'Scan', the API immediately returns a 202 Accepted with a scan ID. The scan runs in the background, updating its progress percentage, and WebSockets (Socket.io) push real-time updates directly to the client's screen."
Q10: What are the current limitations of RepoLens? (Demonstrates maturity!)
Say this: "Currently, RepoLens focuses on the JavaScript and TypeScript (npm) ecosystem. We also enforce a 500 KB per-file limit to protect server memory from minified bundles, and we maintain a human-in-the-loop philosophy—RepoLens creates Pull Requests for developer approval rather than blindly auto-merging code."
