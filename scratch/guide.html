1. Executive Summary & Elevator Pitch

The 30-Second Interview Pitch

"RepoLens is an AI-assisted DevSecOps and code intelligence platform built on the MERN stack. Unlike legacy static analysis tools like SonarQube or Snyk that overwhelm developers with noisy rule codes and zero contextual assistance, RepoLens scans GitHub repositories for hardcoded secrets, dependency CVEs, and dangerous code patterns, translates findings into plain-English explanations, and provides 1-click automated Pull Requests that remediate vulnerabilities directly on GitHub. It also features a RAG-powered codebase Q&A engine, dynamic Mermaid architecture diagrams, CycloneDX SBOM generation, and automated security regression detection."

The Core Problems RepoLens Solves

  1. Developer Alert Fatigue & Cryptic Jargon: Traditional scanners dump identifiers like CWE-78: Improper Neutralization of Special Elements used in an OS Command. Normal developers don't know what to do. RepoLens provides a single plain-English explanation, shows the exact vulnerable line in red, and provides an emerald-green safe drop-in fix.
  2. Remediation Friction: Pointing out a flaw without fixing it creates massive technical debt. RepoLens connects to the GitHub Git Data API to automatically branch, patch, and open a ready-to-merge Pull Request with one click.
  3. Context-Blind Audits: Security tools ignore overall architecture. RepoLens scans routes, data models, and directory trees to synthesize real-time Mermaid.js diagrams and provides an embedded RAG assistant ("Ask Repo") to query the codebase.
  4. Heavy Infrastructure Costs: Traditional solutions mandate external Redis instances, Docker daemons, or Celery queues. RepoLens was re-engineered into a pure MERN architecture using an in-process MongoDB-backed queue, eliminating Redis while maintaining high throughput.

2. System Architecture & Engineering Design

High-Level Architecture

RepoLens follows a decoupled, monorepo architecture divided into three discrete workspaces:

  • client/: React 18 Single-Page Application (SPA) powered by Vite, Tailwind CSS, Lucide icons, Recharts, and Mermaid.js. Locked permanently to dark mode.
  • server/: High-throughput Express + Node.js backend written in strict TypeScript. Implements REST APIs, WebSocket streaming (Socket.io), and the MongoDB job queue.
  • shared/: Centralized TypeScript library containing isomorphic Zod validation schemas, data contracts, and severity calculation utilities. Shared across client and server.

Why Pure MERN (and Why Redis Was Removed)?

In earlier iterations, the system utilized BullMQ and Redis for queueing. In the production refactor:

  • Zero Extra Infrastructure: Redis requires dedicated provisioning, health-checks, memory eviction configurations, and costs money on cloud hosts (like Render/Railway).
  • In-Process MongoScanQueue: We built an asynchronous, in-process worker backed by MongoDB's Scan document state. It processes jobs with a concurrency limit of 3, writes real-time progress to MongoDB, and automatically recovers abandoned or pending scans on server restart.
  • Transactional Persistence: Scan state, findings, and queue jobs reside in the same database engine, preventing split-brain states where Redis holds jobs for nonexistent MongoDB records.

3. Deep Dive into the 4 Core Security Engines

Engine 1: High-Entropy Secrets & Token Scanner

The secrets scanner uses a two-tier detection model: Deterministic Regex Matching combined with Shannon Entropy Calculation.

Shannon Entropy Mathematical Model

Randomly generated API keys, private certificates, and credentials have significantly higher information entropy than normal source code identifiers. The entropy \(H\) of a string \(S\) is computed as: 

H(S) = - ∑ ( p(c) * log2( p(c) ) )

Where \(p(c)\) is the frequency of character \(c\) divided by the total string length.

  • Standard English variable names (e.g., userAuthenticationController) typically evaluate to an entropy between 2.0 and 3.2.
  • Cryptographic base64/hex keys (e.g., AKIAIOSFODNN7EXAMPLE, sk_live_51Oz...) evaluate to 4.5 or higher.
  • RepoLens evaluates any string literal over 16 characters matching key assignment heuristics (e.g. apiKey = "...") against a threshold of 4.5.

Zero-Exposure Masking

To ensure user compliance and zero data leaks, secrets are never stored raw in MongoDB or transmitted across WebSockets. The maskSecret() utility replaces the inner 70% of the token with asterisks (e.g., ghp_1234567890abcdef $\rightarrow$ ghp_12****cdef).

Engine 2: Insecure Code Patterns & AST Analysis

Detects vulnerabilities that linters miss by scanning code structure for exploitable sinks:

  • OS Command Injection: Identifies calls to child_process.exec() or execSync() where template literals (`kill ${pid}`) or string concatenation are passed. Recommends safe argument array execution using execFile() / execFileSync().
  • Dynamic Code Execution: Flags eval() and new Function() with dynamic inputs.
  • Missing Security Headers: Scans Express initialization files (express()) and warns if helmet() middleware is absent.

Engine 3: Dependency Vulnerability & CVE Scanner

Scans package.json and lockfiles against the Open Source Vulnerabilities (OSV) database. It parses semver constraints and reports exact CVE identifiers, vulnerable version ranges, and patched release targets.

Engine 4: CycloneDX v1.5 SBOM & License Compliance

  • CycloneDX v1.5 JSON: Generates machine-readable software bills of materials containing Package URLs (pkg:npm/express@4.18.2), component UUIDs, and dependency trees.
  • License Classifier: Categorizes licenses into Permissive (MIT, Apache 2.0, BSD), Weak Copyleft (LGPL, MPL), and Strong Copyleft (GPL, AGPL) to alert businesses if their proprietary code risks open-source license infection.

4. AI Architecture, RAG Pipeline, & Auto-Remediation

1-Click AI Auto-Remediation (Pull Request Engine)

When an issue is detected, RepoLens doesn't just display an error—it offers 1-click GitHub Pull Request creation. Here is how the backend interacts with GitHub's Git Data API:

  1. Branch Creation: Retrieves the default branch head commit SHA via GET /repos/:owner/:repo/git/ref/heads/:branch and creates a feature branch repolens/fix-[shortId] via POST /repos/:owner/:repo/git/refs.
  2. File Blob Patching: Fetches the existing file's base64 content and SHA. Decodes the file, replaces the vulnerable snippet with the AI-suggested safe replacement, base64 encodes it, and pushes a commit via PUT /repos/:owner/:repo/contents/:path.
  3. Pull Request Creation: Issues a POST /repos/:owner/:repo/pulls with an automated PR title, description of the vulnerability, and a markdown diff explaining the fix.

RAG Pipeline: "Ask Repo AI"

Developers can ask questions like "How does our authentication middleware validate tokens?" or "Are any user endpoints missing authorization checks?":

  • Semantic Chunking (ragChunker.ts): Splits repository files into logical overlapping chunks (800–1200 characters), ensuring function declarations and context boundaries remain intact.
  • Chunk Indexing: Chunks are stored in MongoDB with file paths, line ranges, and language metadata.
  • Context Retrieval: When a user submits a query, relevant code chunks are retrieved using multi-keyword lexical matching and fed into the LLM system prompt.
  • Cited Streaming Responses: The LLM generates streaming markdown with clickable line range citations (e.g., [server/src/middleware/auth.ts:15-32]).

Automated PR Security Reviews

RepoLens automatically listens for GitHub pull_request webhooks. When a PR is opened or synchronized, RepoLens scans the pull request branch and uses postPullRequestComment to comment directly on the PR with the score, issue breakdown, and links.

5. Security Architecture & Defense-in-Depth

1. Token Encryption at Rest (AES-256-GCM)

GitHub personal access tokens and OAuth tokens allow reading private code. If the database is compromised, raw tokens would be catastrophic. 

Ciphertext = AES-256-GCM(plaintext, TOKEN_ENCRYPTION_KEY, IV)
Stored string = IV (12 bytes) : AuthTag (16 bytes) : Ciphertext (hex encoded)
  • Galois/Counter Mode (GCM): Provides both confidentiality and authenticity. If an attacker modifies even a single bit of the encrypted token in MongoDB, decryption fails with an authentication error.
  • Unique IV per Record: Every token is encrypted with a freshly generated 12-byte initialization vector (crypto.randomBytes(12)), preventing rainbow table attacks.

2. Double-Submit CSRF Cookie Protection

Prevents Cross-Site Request Forgery on all state-changing endpoints (POST, PATCH, DELETE):

  • On initial authentication, the server writes a random CSRF token to an HTTP-only signed cookie (_csrf).
  • The client reads this token from the API and must submit it in the custom header X-CSRF-Token on mutating requests.
  • The requireCsrf middleware verifies that the header strictly equals the cookie token.

3. Cross-User Repository Ownership Isolation (Multi-Tenancy)

Every route querying a repository (e.g., /api/repos/:id, /api/scans/:id) enforces: 

const repo = await Repo.findOne({ _id: repoId, userId: req.user._id });
if (!repo) throw new AppError(404, 'Repository not found');

Returning 404 Not Found instead of 403 Forbidden prevents user enumeration and information disclosure.

4. Ephemeral Sandboxed Code Analysis

RepoLens never clones untrusted repository files onto the host operating system disk, nor does it execute user scripts (no npm install or eval). File contents are streamed directly from GitHub's Trees API into memory buffers, analyzed via AST/regex, and immediately released to the V8 garbage collector.

6. Comprehensive Interview Q&A Cheatsheet

Architecture Q1: Can you describe the high-level architecture of RepoLens?
Answer: RepoLens is an end-to-end code security and architecture intelligence platform built on a pure MERN stack (React 18 SPA + Vite, Node.js + Express, MongoDB). The frontend communicates with Express via typed REST endpoints and Socket.io for live scanning progress. Instead of relying on an external Redis/BullMQ queue, we built an in-process, MongoDB-backed queue (MongoScanQueue) that processes scan jobs with concurrency controls, stores findings, and computes security scores asynchronously.
DevOps / Queue Q2: Why did you eliminate Redis and BullMQ in favor of an in-process MongoDB queue?
Answer: Two main reasons: operational complexity and state consistency. Running Redis alongside MongoDB requires managing two separate persistence engines, provisioning memory alerts, and paying for multiple managed services in cloud deployments like Render or Vercel. By implementing MongoScanQueue, we achieved transactional persistence—if a scan fails or the server restarts, pending scans are recovered directly from MongoDB without orphaned queue states or connection timeouts.
Security Q3: How do you securely store and handle users' GitHub OAuth access tokens?
Answer: Tokens are encrypted at rest using AES-256-GCM. We generate a unique 12-byte initialization vector (IV) for every encryption operation using Node's native crypto.randomBytes(12). The resulting ciphertext, IV, and 16-byte authentication tag are packed and saved to MongoDB. Tokens are decrypted strictly in memory at the exact moment a GitHub API call is made, and are never logged or exposed to the client.
Algorithms Q4: How does your secrets detection engine differentiate between random credentials and normal code identifiers?
Answer: We combine regex pattern matching for known token prefixes (like AWS AKIA... or Stripe sk_live_...) with Shannon Entropy calculation. Normal code variables have low entropy (typically 2.0 to 3.2) because vowels and common letters recur frequently. Cryptographically random tokens exhibit high informational entropy (above 4.5). Strings matching secret-like variable assignments that exceed our 4.5 threshold are flagged as leaked credentials.
Full Stack Q5: How does the 1-click AI Auto-Remediation feature work behind the scenes?
Answer: When a user clicks "Open Fix PR", the backend retrieves the repository's default branch commit SHA, creates a new Git reference (e.g. refs/heads/repolens/fix-abc123), retrieves the target file's blob SHA, applies the AI-suggested safe replacement, commits the patched file via GitHub's Contents API, and issues a POST /repos/:owner/:repo/pulls request. The returned PR URL is saved to the finding and displayed to the user.
AI / RAG Q6: How does the "Ask Repo AI" RAG pipeline work without running out of token limits?
Answer: Rather than dumping whole files into the LLM prompt, we chunk repository files into 800–1200 character segments with line number tracking and store them in a MongoDB Chunk collection. When the user asks a question, we perform lexical search against the chunk index to retrieve only the top relevant context blocks. These blocks are passed to Claude or Gemini alongside a strict system prompt instructing the model to provide cited answers.
Security Q7: What is Security Regression Detection and how did you implement it?
Answer: Security regression occurs when a new commit decreases the overall security score or introduces new vulnerabilities. On each completed scan, RepoLens fetches the immediate previous scan for that repository and calculates scoreDelta = currentScore - previousScore. If scoreDelta < 0, we mark isRegression = true and tag any newly detected finding with isRegressionNew = true. The frontend highlights this with a regression alert banner and a filter to isolate only the new issues.
Full Stack Q8: How do you handle GitHub API rate limits when scanning large repositories?
Answer: Our githubRequest client implements ETag caching (HTTP 304 Not Modified) with an in-memory LRU map of 500 entries, saving rate limit tokens for unchanged trees. Furthermore, it inspects the x-ratelimit-remaining and x-ratelimit-reset response headers; if the client reaches rate limit barriers, it initiates exponential backoff with jitter up to 10 seconds before retrying.
Compliance Q9: What is an SBOM and what standard does RepoLens support?
Answer: A Software Bill of Materials (SBOM) is a complete formal inventory of all software components, libraries, and modules used in an application. RepoLens implements the industry-standard CycloneDX v1.5 specification. It parses direct and transitive dependencies from package.json, assigns valid Package URLs (PURLs), and exports a downloadable JSON file.
Web Security Q10: Why did you use Double-Submit CSRF cookies instead of simple Origin headers?
Answer: Origin and Referer headers can be stripped or altered by certain enterprise proxies, browser extensions, or intranet gateways. The double-submit cookie pattern ensures that any state-changing request must carry the CSRF token in both a secure cookie and an explicit request header. Because same-origin policy prohibits malicious cross-origin scripts from reading or writing our domain's headers, CSRF attacks are blocked.
Performance Q11: How is the security score calculated?
Answer: We start with a baseline score of 100 and apply weighted deductions based on active open findings: Critical issues deduct 25 points, High deducts 15 points, Medium deducts 5 points, and Low deducts 2 points. The result is clamped between 0 and 100. When a user marks a finding as resolved or ignored (false positive), the score automatically recalculates.
Deployment Q12: How can RepoLens be deployed in production?
Answer: RepoLens supports dual deployment modes: 1. Split Deployment: The React Vite SPA is deployed to Vercel (with client-side SPA route rewrites configured in vercel.json) and the Express API is deployed to Render or Railway with MongoDB Atlas. 2. Monolithic Single-Container: In production mode (NODE_ENV=production), Express automatically serves the built static client bundle from client/dist, allowing the whole platform to run inside a single Docker container.
AppSec Q13: How does RepoLens prevent command injection in its own backend when scanning files?
Answer: RepoLens never uses shell execution commands (exec, spawn, bash) to analyze repository files. File contents are fetched over HTTPS through the GitHub REST API and parsed purely in memory using JavaScript string methods and static Abstract Syntax Tree (AST) parsers. No user code is executed on the server.
Frontend Q14: How does the client maintain real-time updates while a scan is running?
Answer: We use Socket.io. When a scan job progresses in the background (e.g. fetching files at 10%, secret scanning at 25%, AST pattern analysis at 55%, SBOM generation at 85%), the worker emits scan:progress events targeted to the user's private socket room. The React component listens for these events to update the animated progress bar in real time without polling.
Architecture Q15: If an interviewer asks: 'What was the hardest technical challenge you solved on RepoLens?', how should you answer?
Answer: "The hardest challenge was refactoring the architecture from a distributed setup requiring Redis and BullMQ to a pure MERN in-process event-driven engine without sacrificing reliability. We had to implement an asynchronous queue with bounded concurrency in Node.js, ensure crash recovery by inspecting pending MongoDB records on startup, and eliminate re-render loops in the React SPA when synchronizing authentication state and WebSocket progress. This reduced our deployment footprint by 50% and made the system zero-maintenance."
